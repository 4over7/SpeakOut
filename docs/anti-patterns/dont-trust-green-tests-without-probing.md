# 别把「测试是绿的」当成「这条路径被验证过」

## 真实事件

**2026-08-14 ~ 08-16，云账户持久化连续 31 轮 review。** 期间出现 **4 次**「测试全绿、断言也在，但被验证的那条路径压根没跑到」，其中 2 次我已经写进 commit message 声称「实测能抓到」。

| # | 假象 | 真相 |
|---|---|---|
| 1 | 「回滚写列表已验证」 | 注入标志一直开着，回滚里那次 `_saveAccounts()` 必然也抛 —— 探针显示 `PROBE_ROLLBACK_LIST_OK` **一次都没出现** |
| 2 | 「去掉回滚写列表会被抓到」 | 探针显示去掉与不去掉磁盘状态**完全一样**，那行在当时的顺序下确实冗余 |
| 3 | 「初始化失败重试已验证」 | 用 `debugFailPersistence` 注入，它在 `_requirePrefs` 抛；而 `_doInit` 走 `getInstance()`，根本不经过 —— 测的是另一条路径 |
| 4 | 「并发串行化已验证」 | 两次调用写在同一同步块里，链还没开始跑，`_inSerializedWrite` 的危险窗口压根没覆盖 |

第 2 条尤其反直觉：探针**没错**，是被验证的**场景不对** —— 注入点在碰 `SharedPreferences` 之前就抛了，没有污染缓存，而真实故障下 `_setValue` 会**先更新 `_preferenceCache` 再 await 平台写入**，失败时缓存不回滚。换成模拟真实形态的注入后，同一行代码立刻从「冗余」变成「必需」。

## 为什么会发生

写测试的人和写实现的人是同一个，于是**注入点按「我以为的失败形态」放**，而不是按真实故障的形态放。断言随后基于这个失真模型写出来，红绿看起来都对。

三种典型走样：

- **注入太早** —— 在真正的副作用发生前就抛，于是「补偿是否有效」根本没被触发
- **注入太粗** —— 布尔式「全都失败」，掩盖了「部分成功、部分失败」这个真正危险的中间态
- **窗口没覆盖** —— 并发测试写在同一同步块里，异步交错的那个窗口从未进入

## 如何避免

**改动生效性靠探针确认，不靠红绿。**

```dart
// 在被验证的那一步打点，跑一遍看它到底有没有执行
await _saveAccounts();
// ignore: avoid_print
print('PROBE_ROLLBACK_LIST_OK');
```

跑完数一下出现次数。是 0，就说明这条断言在空转 —— 无论它是绿是红。

配套三条：

1. **注入点必须复刻真实失败形态。** 存储层是「先改内存缓存、再 await 平台」，注入就要先写再抛；逐 key 循环是「部分已删、最后聚合抛」，注入就要放进循环里而不是方法开头。
2. **只失败第 N 次，而不是全都失败。** 布尔注入会把补偿路径一起挡掉 —— 补偿里那次写入永远跑不到。用计数器（`debugFailAccountsWrites = 1`）让首次失败、补偿成功。
3. **并发测试要制造真实交错。** 在两次调用之间插一个 `await Future.delayed(...)`，让第一个操作先进入它的 await 间隙。写在同一同步块里等于没测并发。

清探针时**精确回退那几行**，不要整文件 `git checkout` —— 我这么干过一次，把同批未提交的实现改动一起回退了，下一次验证的现象完全对不上，白查一轮。
