# 不要用「源码里找得到这段字符串」冒充「代码这么执行」

## 真实事件

**2026-08-16 ~ 08-18，剪贴板注入链连审 13 轮。** 生产缺陷早在第 44 轮就清零了
（P0/P1 无），可 review 每轮还能报出一批 P2 —— **全是我写的断言能被变异骗过**。
同一个错误换了三种面孔：

| 轮次 | 我以为的判据 | 实际证明不了 |
|---|---|---|
| 42 | 位置先后（`indexOf(A) < indexOf(B)`） | ≠ 包含关系。A 在 B 之前，不代表 B 在 A 的分支里 |
| 43 | 同块共现（块里同时有 `if (cond)` 和 `doIt()`） | ≠ 受该条件保护。`const BOOL x = cond; doIt();` 也满足 |
| 44 | 字符串出现（`body.contains('return')`） | ≠ 代码里存在。`log("{ return }")` 也满足 |

对方给的诱饵只要一行：

```objc
log_to_file("if (gen == 0) if (_txHoldDepth == 0) tx_abandon_locked()");
```
```dart
if (false && msgTaskId != _taskId) { return; }
```

每轮我都把判据做得更精细一点（换正则、配平括号、跳字符串），**下一轮它还能再造一批**。

## 为什么会发生

源码级断言便宜、不需要跑起来，写的时候有种「我把这行钉住了」的踏实感。
但它锚定的是**文本形态**，而形态和语义之间永远有缝：

- 同一语义有无数种写法（`return 0;` / `return (uint64_t)0;` / `return kNone;`）
- 同一文本可以出现在不执行的位置（字符串、注释、永假分支、closure）
- 判据本身会随实现演进失效（签名改了、判据换了、语句挪进了 helper）

**最危险的不是假红，是假绿** —— 断言还在、测试还绿，但它守的那件事已经没人守了。

## 如何避免

**分清两种断言，别混用：**

| 类型 | 能证明 | 该用在 |
|---|---|---|
| 源码级 | 「代码还长这样」 | 防形状退化：命名约定、分层依赖、必须存在的 guard |
| 行为级 | 「这么执行会得到什么」 | 语义正确性：状态机、交错、失败路径 |

**语义正确性一律走行为级测试。** native 代码也能做到：
把实现文件 `#include` 进测试宿主拿到 static 函数，用**独立资源**
（`pasteboardWithUniqueName`）驱动，宏掉副作用（`CGEventPost`），
失败注入用 runtime swizzle。参见 `native_lib/tests/tx_harness.m`。

**非要写源码级断言时，三条底线：**

1. 有 AST 就别用字符串 —— Dart 侧有 analyzer，用节点包含关系而不是 offset 比较
2. 「多处出现」的场景永远不用第一个匹配（`indexOf` 取第一个这个错，我一天犯了四次）
3. **写完立刻变异验证**：把被守护的那行删掉/改坏，确认测试真的红

第 3 条最关键。这一整条链里，变异探针一共抓出 **6 条我自己写的空转断言**，
每一条都是我写完自以为没问题的。

## 修复模式

发现某条断言可被诱饵绕过时，**不要只补那一个特例**（换个写法就又绕过去了）。
问一句：**这条断言想证明的是形态还是语义？**

- 形态 → 升级判据强度（AST、词法感知、结构匹配）
- 语义 → **换成行为测试**，源码断言降级为辅助
