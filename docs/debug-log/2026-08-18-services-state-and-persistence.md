# Services 状态与持久化边界（2026-08-18）

## 第一轮：启动失败被 Ready 覆盖

### 现象

`AppService._initASR()` 把模型下载和 provider 初始化异常吞掉；最终健康检查只看键盘监听，
因此 CGEventTap 正常但 ASR 不可用时仍显示 Ready。

### 假设·判断原因

启动状态把「能收到快捷键」误当成「应用可听写」，并且内外两层 catch 的错误所有权冲突。

### 措施

ASR 初始化失败统一 rethrow 给启动总控；Ready 同时要求 listener 与 ASR 就绪，
标点初始化等后续状态也不能覆盖最终的 ASR 错误。

### 验证结果

启动健康行为测试覆盖两项条件的组合；Services 487 例通过，全量非下载测试 878 例通过、10 例按设计跳过。

### 复盘

健康状态应描述用户功能是否可用，而不是某个底层组件是否启动。

## 第二轮：聊天清空与历史文件完整性

### 现象

新增消息走写队列，`clearHistory()` 却直接写同一个 JSON；stream 还暴露内部可变列表。
串行化之后，最终文件仍被直接 truncate，进程在写入窗口退出会留下半截 JSON。

### 假设·判断原因

内存动作、事件快照和磁盘提交被当作三件无关操作，没有共享同一事务边界。

### 措施

所有写动作进入同一 Future 链；stream 发送不可变快照；JSON 先写同目录 staging、flush 后原子 rename。

### 验证结果

确定性交错测试证明清空不会与在途写并发；事件快照不可变且保留当时版本；
晋升暂停时最终文件仍是上一版完整 JSON，放行后才整体切换。

### 复盘

「没有并发写」只解决进程内竞态，不能替代崩溃一致性；用户数据文件还需要原子提交。

## 第三轮：未完成 DMG 被当成完整缓存

### 现象

断点数据直接写最终 `.dmg`，重启后只要超过 20 MB 就进入 ready；
206 缺少可信 `Content-Range` 时同样可能晋升。

### 假设·判断原因

文件大小只能证明「下载过一些」，不能证明响应完整，也不能区分旧版本遗留的半包。

### 措施

下载中固定写 `.part`；只有字节数与 Range 总长一致后才 rename 为最终 DMG，
并写入匹配实际长度的完成标记。缓存复用同时验证最终文件、最小体积和完成标记；
206 必须声明与本地断点一致的起点及有效总长。

### 验证结果

本地 HTTP 行为测试先返回 21 MB/22 MB，确认只保留 partial，再续传完成并晋升；
另一个 21 MB 稀疏 partial 配无 Content-Range 的 206，确认保持 failed。macOS Debug 构建成功。

### 复盘

完成态必须由协议证据和原子状态转换共同建立，不能从「看起来够大」推断。

## 第四轮：浮窗异步错误与旧 timer 覆盖新状态

### 现象

同步 try/catch 包住 `MethodChannel.invokeMethod()` 捕不到 Future 上的 PlatformException；
上一轮成功提示的延迟清空也会擦掉下一次录音的实时文字。

### 假设·判断原因

调用发起与异步完成被混为一谈，timer 又没有携带状态所有权。

### 措施

controller 内 await 并消化通道异常；每次新浮窗状态推进 generation，旧 timer 只清自己的 generation。

### 验证结果

模拟 PlatformException 不产生未处理异常；新录音文字出现后，旧 timer 不再发送空状态。
`flutter analyze` 无问题。

### 复盘

延迟任务必须证明自己仍拥有当前状态，不能仅凭「时间到了」执行副作用。
