# 语音注入贴出上一次识别的文字（线上现象）

## 第一轮

### 现象

2026-08-16 晚，用户报告：一次语音输入后，**粘贴出来的是上一次语音识别的文字**，
不是刚说的这一句。

### 前提先钉死（避免归因到本会话的改动上）

- 用户运行的是 `/Applications/SpeakOut.app`，**v1.10.0 build 241**，
  其 `libnative_input.dylib` 时间戳 **8/14 16:26**。
- `strings` 查该 dylib：`Clipboard tx` 匹配数 **0** —— 本会话（8/16）对剪贴板
  事务协调器的全部改动**都不在这个二进制里**。
- 结论：**这是线上现存缺陷的一次真实复现，不是本会话改出来的。**

### 日志能证明什么

日志目录取自 plist（`flutter.log_directory = ~/Apps/speakout/log`），verbose 已开。

事故时间窗三次连续 PTT（均为 toggle 模式，模式 ptt，云端 Volcengine ASR）：

| 结束时刻 | ASR 结果 | inject/save done |
|---|---|---|
| 19:31:00.97 | 106 字 `#9d2ced` | 19:31:02.11 |
| 19:31:53.56 | 39 字 `#be820b` | 19:31:53.90 |
| 19:32:13.51 | 40 字 `#2df7c4` | 19:32:14.84 |

由此**可以排除**两条：

1. **「`CLIPBOARD_RESTORE_DELAY_MS`(800ms) 内连注两次」不成立。**
   相邻两次注入间隔 51.8s 和 20.9s，差了一到两个数量级。
2. **AI 润色 / 打字机流式路径没有参与。** `inject/save done` 距 ASR 返回只有
   ~40ms，中间没有 LLM 调用；走的是一次性 `inject_via_clipboard`，
   不是 `inject_clipboard_begin/chunk/end`。

三次 ASR 结果内容哈希互不相同，说明**识别本身没错**，错在识别之后。

### 日志不能证明什么 —— 这本身是最该修的一条

`native_input.m` 里 **`inject_via_clipboard` 全函数零日志**。
出货 dylib 里 clipboard/inject 相关字面量只有 3 条，全属于流式路径。

于是这次事故在原生日志里**一行痕迹都没有**：
不知道快照拍到了什么、`clearContents` 返回的 changeCount 是多少、
Cmd+V 发出前剪贴板里到底是不是我们刚写的文字、800ms 后的还原走没走。

**文本注入是这个产品最核心的一步，而它在日志里完全不可见。**
排查只能靠推理，这是这轮最该先补的窟窿。

### 假设 · 判断原因（未验证，按可能性排序）

**A. 还原被跳过，上一次的注入文字滞留在剪贴板。**
出货代码的还原判据是：

```objc
dispatch_after(800ms, ...) {
  if (pasteboard.changeCount != ourChangeCount) return; // 跳过还原
  ...
}
```

只要这 800ms 内有任何人动过剪贴板，还原就被跳过，**我们注入的文字永久留在剪贴板**。
本机没有第三方剪贴板管理器，但系统的 `SSPasteboardHelper`（屏幕共享剪贴板同步代理）
在跑，它会观察并可能触碰剪贴板。

**B. Cmd+V 早于新内容生效，贴出了剪贴板里的旧内容。**

```objc
[pasteboard setString:newText forType:NSPasteboardTypeString];
usleep(10000);            // 10ms —— 纯猜的等待，没有任何校验
post_command_key(9, kCGHIDEventTap);   // Cmd+V
```

写完剪贴板只睡 10ms 就发 Cmd+V，**没有任何一步确认目标进程看到的已经是新内容**。
跨进程 pasteboard 可见性没有时限保证，机器忙的时候这 10ms 完全可能不够。

**A + B 叠加正好解释现象**：A 让上一次的注入文字留在剪贴板，
B 让这一次的 Cmd+V 贴出的仍是那份旧内容 —— 用户看到的就是「上一次识别的文字」。

需要强调：**A、B 都是推理，日志给不出证据**（因为根本没日志）。
在补上日志、拿到一次带证据的复现之前，不把任何一条当成定论。

### 措施

1. **给一次性注入路径补齐日志**（本轮必做）：快照条数、`clearContents` 返回值、
   发 Cmd+V 前剪贴板里实际内容的指纹、还原走没走 / 为什么没走。
   没有这些，下次复现照样只能猜。
2. **把「睡 10ms」换成「校验通过才发 Cmd+V」**：写完之后轮询确认
   `stringForType:` 读回来的就是我们写的那份，确认不到就放弃这次注入
   （宁可不注入，也不要把上一次的文字贴进用户的文档）。
3. 还原被跳过时**记明原因**（changeCount 对不上 / 快照不可信），
   把「静默跳过」变成「日志里查得到」。

本会话正在重写的事务协调器**并没有修掉这两条** —— `tx_paste_locked` 里同样是
`usleep(10000)` 之后直接发 Cmd+V。所以这不是「已经修好了、只是没发版」，
而是一条独立的、仍然存在于最新代码里的缺陷。

## 第二轮：把「猜」变成「查得到 + 拦得住」

### 措施（已实施）

1. **发 Cmd+V 之前校验剪贴板确实生效。**
   `tx_paste_locked` 写完之后轮询 `stringForType:`，读回来与写进去的一致才发键，
   最多等 200ms（40 × 5ms）；超过 5 次轮询才拿到会记一行「花了多少 ms」。
   **校验不过就不发 Cmd+V** —— 宁可这次注入失败，也绝不把上一次的识别结果
   贴进用户文档。这是取代原来那句 `usleep(10000)` 的关键改动：
   把「等 10ms 应该够了吧」换成「确认到了才动手」。

2. **注入失败不再静默。** `inject_text` 从 `void` 改成返回 `int`
   （Linux/Windows 两个实现同步改签名 —— Dart 侧按 `Int32` 绑定，
   那边若还是 `void`，读到的返回值是垃圾）。
   `CoreEngine` 收到 false 时发 `EngineStatus.error("注入失败，文字已存到聊天记录")`，
   并且**照常把文字写进聊天记录**——那是用户唯一能找回这段话的地方。

3. **一次性注入路径补日志**：长度、代次、是否失败、剪贴板迟到多久、
   还原走没走 / 为什么没走（changeCount 对不上 vs 快照不可信）。
   下次再复现，日志里查得到，不用再靠推理。

### 仍未解决 / 需要真机验证

- **候选 A（还原被跳过导致上一次的文字滞留剪贴板）没有被这轮改动消除。**
  本会话的事务协调器让「800ms 内连注两次」不再丢原内容，但「800ms 内**别人**
  动了剪贴板 → 跳过还原 → 我们的文字留在剪贴板」这条依然成立。
  这是有意的：那种情况下用户手里是他自己刚复制的东西，硬还原会盖掉它。
  代价是我们的注入文字可能留在剪贴板里。**这是取舍，现在至少日志里看得见。**
- 本轮改动**尚未在真机验证**。需要装上新版后复现一次，确认：
  (a) 正常注入时日志有 `Clipboard tx: inject ...` 行；
  (b) 制造慢速场景时能看到「pasteboard took Nms」或「never reflected」；
  (c) 注入失败时 UI 真的弹出提示。

## 第三轮：拿到决定性证据，机制定名

### 现象（补充）

用户提出假设：**云端模式下从送音频到拿回文字这段太长，剪贴板还没开始动。**

### 判断原因

这个假设可以直接用日志证伪 —— **我们自己合成的 Cmd+V 带 `SPEAKOUT_SYNTHETIC_MARK`，
在 tap 回调开头就被滤掉，不会进日志**。所以日志里出现的 `code=9` 一定是真人按的。
左 Command 的设备位是 `0x8`，基线是 `0x100`，因此真实 Cmd+V 就是 `mods=0x108`。

| 时刻 | 事件 |
|---|---|
| 19:32:13.51 | 最后一次录音结束 |
| 19:32:14.85 | 注入完成（40 字 `#2df7c4`），**此后再无任何录音** |
| 19:37:09.97 / :11.85 / :23.05 | `code=9 mods=0x108` —— 真实 Cmd+V ×3 |

**粘贴发生在注入之后 4 分 55 秒。** 由此：

- **用户的假设不成立**：粘贴根本不在任何 ASR 等待窗口里，差了 5 分钟。
- **第一轮的候选 B（10ms 传播竞态）也不是本次原因**：那影响的是注入当下，
  管不到 5 分钟后的一次手动粘贴。
- **只剩候选 A，并且被坐实**：那次注入的文字一直留在剪贴板里没被还原，
  用户 5 分钟后 Cmd+V 贴出来的自然就是它。

顺带量了云端 ASR 耗时（29 个样本）：**最小 300ms / 中位 379ms / 最大 5221ms**。
中位数可以接受，**最大 5.2 秒是真问题**，但与本次故障无关，另记。

### 根因

还原判据错了。出货代码（以及本会话此前的全部改动）都在比 `changeCount`：

```objc
if (pasteboard.changeCount != ourChangeCount) return; // 跳过还原
```

**`changeCount` 会被任何「重新声明 pasteboard」的旁观者推高，不只是用户复制。**
这台机器上正跑着 `SSPasteboardHelper`（屏幕共享的剪贴板同步代理），
它一动，我们就永远判定「用户易主」而跳过还原 —— 注入的文字于是永久滞留。

真正要区分的是**内容**：剪贴板里现在还是不是我们放进去的那份？
是 → 没人真正接管过，还原天经地义；不是 → 用户确实换了，别去盖他的。

### 措施

`tx_finish_locked` 的判据从「`changeCount` 没变」改成
「`stringForType:` 读回来的内容 == 我们最后写进去的 `_txLastInjected`」。
本事务一次都没写过剪贴板时（比如 begin/end 之间 LLM 就失败了）退回比 `changeCount`。

### 验证结果

- 新增 3 条断言（还原判据比内容 / 发键前校验 / 注入失败可上报），
  2 个变异探针确认能抓到（退回只比 changeCount、退回固定 10ms 等待）。
- clang 零警告，全量测试通过。
- **真机验证仍未做** —— 需要装机后复现「注入 → 隔几分钟 Cmd+V」，
  确认贴出来的是用户自己的剪贴板内容而不是识别结果。

## 第四轮：探针推翻了我自己的根因

### 现象

第三轮我把根因写成「`changeCount` 被 `SSPasteboardHelper` 这类旁观者推高
→ 永远判成用户易主 → 跳过还原」。写完就该验，于是写了个探针
（`scratchpad/pbprobe.m`）逐字复刻出货代码的动作序列。

### 验证结果

```
before=7067  clearContents返回=7068  clear后=7068  setString后=7068
900ms 后=7068  期间是否有旁观者改动: 没有
```

连采 5 次，**每次都没有旁观者动过 changeCount**。两条结论：

1. `setString:` 在 `clearContents` 之后**不会**再推高 changeCount ——
   所以判据不会被我们自己的写入打败，这个 bug 不是必现。
2. **「旁观者推高 changeCount」在这台机器上拿不到任何证据。**

顺带核对了位掩码（`native_input.m:210/216`）：
`0x8` = `NX_DEVICELCMDKEYMASK`，`0x100` = `NX_NONCOALSESCEDMASK`（基线）。
所以 `mods=0x108` 确实是真实的左 Command + V，**第三轮的时间线证据成立**。

### 复盘（第三轮根因作废）

**我犯了项目准则里明令禁止的那条：没有确定性证据就往系统层推。**
「`SSPasteboardHelper` 在跑，它会碰剪贴板」——「在跑」是事实，
「它推高了 changeCount」是我编的因果。探针一跑就塌了。

更难堪的是：这跟第三轮我批评自己的毛病是同一个。
第三轮我写「用错误的判据去论证一个取舍，取舍本身就是假的」，
然后**立刻用一个没验证的机制去论证一个根因**。

### 当前诚实状态

**已确证：**
- 粘贴发生在注入之后 4 分 55 秒，其间无任何录音 → 排除「ASR 窗口内粘贴」
  和「10ms 传播竞态」。
- `mods=0x108` 是真人按的 Cmd+V（位掩码已核对源码定义）。
- `setString` 不会自打判据。
- 5 次采样内无旁观者扰动 changeCount。

**未确证：** 19:37 时剪贴板里为什么还是那段识别文字。
一个**尚未验证**的可能：只要历史上发生过**一次**还原被跳过，
那段注入文字就成了「用户的剪贴板内容」，此后每次注入都会忠实地把它
快照下来再还原回去 —— 一次失败即永久污染，且看起来像「一直有问题」。
这条同样**没有证据**，不写进结论。

**改动的定位要说准**：把还原判据从 changeCount 换成内容比对，
是一条**严格的健壮性改进**（内容比 changeCount 更能反映「用户是否真的接管」），
但**不能声称它修好了这次观察到的故障** —— 因为故障机制还没查明。

### 又一处我过度声称了（自查发现，codex 没点出来）

第二轮我写「把『睡 10ms』换成『校验通过才发 Cmd+V』」，听起来解决了
候选 B（跨进程传播竞态）。**没有。**

那个校验是在**我们自己的进程里**读回来比对。`setString:` 已经成功的前提下，
这一读几乎必然立刻命中 —— 它证明不了目标 App 看到了新内容。
它真正挡住的只是「setString 声称成功但内容不是我们那份」（比如紧接着
有别的进程重新声明了剪贴板）。

跨进程可见性要真正解决，需要目标进程的粘贴回执，而 macOS 没有这种机制。
注释已改写，不再暗示它解决了候选 B。

### 下一步（唯一能定案的路径）

装上带日志的构建，复现一次。新日志会直接给出：
- `Clipboard tx: inject len=... gen=...` —— 注入确实发生过
- `Clipboard tx: restored` / `skipped restore (clipboard content is no longer ours)`
  / `skipped restore (snapshot was never stable)` —— **还原到底走了哪条分支**

只要拿到这一行，机制就定案了。在那之前不写结论。

## 第六轮：把第五轮标记「未做」的四条做掉

第五轮我列了四条「明确未做」。逐条收口。

### P2-3 持锁做慢操作

三处改动，**其中第一处是我自己造的无用功**：

1. `tx_paste_locked` 里那个 40×5ms 的轮询**删掉，改成读一次**。
   那个轮询是按「等跨进程传播」设计的，但这个读根本不跨进程 ——
   `setString:` 已返回成功的前提下，同进程读回要么立刻就对、要么就是真被接管了，
   再等 200ms 也等不出不同结果，纯粹拉长持锁时间和 UI 阻塞。
2. `inject_clipboard_chunk` 的 `usleep(30000)` 节奏等待**挪到锁外** ——
   它只是给目标 App 留粘贴时间，跟事务状态无关。
3. `copy_selection` 那最长 250ms 的等待**挪到锁外**（放锁 → 等 → 重新取锁）。
   等的是目标 App 响应 Cmd+C，不该让还原任务和别的注入陪绑。
   同步 FFI 调用方仍会阻塞 250ms，那是这个 API 形态的固有代价，未改。

### P2-4 旧 dylib ABI 不匹配

新增 `native_input_abi_version()`，macOS / Linux / Windows 三处都导出，
Dart 初始化时校验。旧 dylib 没这个 symbol → 明确报错，
而不是按 Int32 去调一个还是 void 的旧 `inject_text`、读到返回寄存器里的垃圾。
断言里加了「三个平台 + Dart 侧四处版本号必须一致」。

### P2-5 错误文案硬编码中文

`EngineStatus` 加 `code` 字段（`kind` 早就是为这个准备的）。
引擎发稳定错误码，`main.dart` 的 `_localizedStatus` 映射到 `loc.xxx`。
新增 `engineInjectFailed` / `engineInjectPartial` 两条中英文案。
**既有的那批中文 message 没有一次性重写** —— 那是独立的技术债，
新增的走码、老的逐步替换。

### P3-1 可执行交错测试

**仍未做。** 需要一个能驱动 `tx_*` 的 native 测试宿主，且要绕开合成 Cmd+V
的真实副作用（否则测试会往当前焦点窗口里粘贴）。
这是这条链收敛前的最后一件事，留作单独任务。

### P1-3 纠正了我什么

我因为那个（已被探针证伪的）「旁观者推高 changeCount」理论，
把 `changeCount` 判据**整个换成了 token**。这是过度反应：

- **`changeCount` 恰恰是 Apple 文档里判断 ownership 是否还在自己手上的正规机制**；
- 而 token **不是访问控制** —— general pasteboard 对所有进程可读，别人能原样重放；
- `stringForType:` 会**合并所有**提供该 type 的 item，别人加一个 item
  也可能读出同样的 token。

现在收敛成一个 `tx_still_ours_locked()`，三条缺一不可：
`changeCount == expected` + 恰好一个 item + token 精确匹配。
三个调用点（写前 / copy 前 / 收尾）全部走它，不再各自拼判据 ——
分散写正是「只改一处」的复发温床。

另外 token 写入现在**先写局部变量、检查返回值并读回，全成功才赋给 `_txToken`**：
写失败却记下 token 的话，收尾会**永久**判成「不是我们的」，还原再也不会发生。

### 关于 ABI：断言必须能拦住「忘记升」

原来那条只比「四处数字相等」，而我恰恰是**四处都没改**，所以它全绿。
换成**签名指纹锁**：扫 `native_input.m` 所有导出函数的规范化签名做 SHA1，
钉在测试里。签名一变指纹就变 → 测试红 → 逼你同时升版本号和更新指纹。
探针验过：随便给一个导出函数加个参数，立刻抓到。

### 本轮未做

- **P2-1 的完整版**：codex 建议用一把独立的「注入串行锁」覆盖
  `inject_text` / chunk / copy 全部入口，并把 `_txPasteFailed` 改成
  逐调用返回值。本轮只做到「`inject_text` 整段串行」+「chunk 进入时清标志」。
  彻底改要重排三个入口的锁结构，**留作单独任务**。
- **P2-3 其余 void 导出**（`launch_updater` / `stop_audio_recording` /
  `stop_device_change_listener`）：不在剪贴板链上，**留作单独任务**。
  其中 `launch_updater` 值得优先 —— 它失败时 App 仍会在 500ms 后退出，
  用户会遇到「点了更新，应用关了，什么也没发生」。
- **P3-1 可执行交错测试**：仍未做，这是收敛前的最后一件事。

### 复盘

- **变异探针这轮抓出 2 条我自己写的空转断言**（token 写失败、TOCTOU 核对）：
  把实现改坏，测试照样绿。补上后重验通过。
  到这轮为止，探针一共抓出 **3 条空转断言** —— 每一条都是我写完自以为没问题的。

## 第八轮：把「形状断言」换成「行为证明」

### 为什么换

第 44、45 轮 review 的结论都是「P0/P1 无，生产代码干净」，但每轮仍能报出
一批 P2 —— 全是**我的断言还能被更刁钻的变异骗过**：

```objc
log_to_file("if (gen == 0) if (_txHoldDepth == 0) tx_abandon_locked()");
```
```dart
if (false && msgTaskId != _taskId) { return; }
```

**只要断言基于源码文本，就永远能构造出骗过它的写法。** 我这几轮的错误
换过三种面孔：位置先后 ≠ 包含关系（42）、同块共现 ≠ 受该条件保护（43）、
字符串里出现 ≠ 代码里存在（44）。每次我都只是把判据做得更精细一点，
而 codex 每轮都能再造一批。这不是它挑刺，是**方法本身的天花板**。

### 做法

`native_lib/tests/tx_harness.m`：直接 `#include` 实现文件拿到 static 函数，
用真实的 `tx_*` 跑确定性交错，检查**最终剪贴板内容**。

两条安全前提，都不需要改生产代码：

1. `pasteboardWithUniqueName` —— 不碰用户的通用剪贴板；
2. 先引系统头、**再**宏掉 `CGEventPost` —— 不往当前焦点窗口发任何按键。
   （顺序反了宏会破坏 `CGEvent.h` 里的函数声明本身。）

失败注入用 **ObjC runtime swizzle**（`setString:forType:` 按需返回 NO），
全在测试文件里 —— 不把注入需求塞进实现，这是本项目
[`dont-let-injection-shape-production-code`] 立下的规矩。

### 十个场景

| # | 交错 | 期望 |
|---|---|---|
| 1 | X → 注入 A → 收尾 | 还原 X |
| 2 | X → 注入 A → 用户复制 Z → 收尾 | 保留 Z |
| 3 | X → A → 用户复制 Z → 注入 B → 收尾 | 还原 Z（不是 X） |
| 4 | 空 → 注入 A → 收尾 | 注入确实发生 + 回到空 |
| 5 | X → begin → chunk A → chunk B → end | 还原 X |
| 6 | X → 注入 A → 别人写了同样的 "A" | 保留对方的（内容相同也不认） |
| 7 | X → 注入 A → 注入 B → 收尾 | 还原 X（不是 A） |
| 8 | X → begin（未写入）→ 用户复制 Z → end | 保留 Z |
| 9 | 快照标记不可信 → 收尾 | 保持现状，不拿垃圾覆盖 |
| 10 | setString 注入失败 | 返回非零 + 仍还原 X（不能留空） |

### 验证结果

**建这些场景的过程本身就是收获 —— 前三轮共有 5 个场景「测试绿但证明不了」：**

- 场景 2/6 互为冗余：去掉 changeCount 判据时 token 挡住了，去掉 token 时
  changeCount 挡住了 —— 两条单独都抓不到。补场景 8
  （事务未写入过、`_txToken` 为 nil，判据只剩 changeCount）才区分开。
- 场景 3 抓不到「事务已开启仍重拍快照」：那条交错里重拍与不重拍结果相同。
  补场景 7（连注两次、无外部干扰）才抓到 —— 那正是第 33 轮的 N3 丢数据缺陷。
- 场景 4 抓不到「空剪贴板被当成读取失败」：「拒绝注入」与「还原成空」
  最终状态一样。加上「注入必须真的发生」才区分开。
- `_txOriginalValid` 与 setString 失败路径自然触发不了，分别用直接置位和
  swizzle 注入补上。

最终 **8 个语义变异全部抓到**，其中三条是历史上真实发生过的 P1：
事务已开启仍重拍（第 33 轮 N3）、写前不查易主（第 40 轮）、
setString 失败返回 0（第 43 轮）。

已接进 `flutter test`（macOS 专属，其它平台 skip）。测试里同时断言
「宿主必须用 unique pasteboard」「必须宏掉 CGEventPost」「不得出现
generalPasteboard」—— 安全前提本身也是判据的一部分。

### 复盘

- **这才是这条链从第 35 轮起就该做的事。** 中间十轮把精力花在
  「让源码断言更难被骗」上，收益递减且永远到不了头。
- 但那十轮不是白费：每一轮修掉的都是**真实的生产缺陷**，
  而且正是它们逼出了现在这批交错场景 —— 场景 3/7/10 直接来自
  第 33/40/43 轮的 P1。
- **新测试写完必须立刻变异验证**，这次又验出 5 个「绿但无证明力」的场景。
  「写完就以为完事」是这整条链里我重复最多次的错误。
