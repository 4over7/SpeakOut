# 语音注入贴出上一次识别的文字（线上现象）

## 第一轮

### 现象

2026-08-16 晚，用户报告：一次语音输入后，**粘贴出来的是上一次语音识别的文字**，
不是刚说的这一句。

### 前提先钉死（避免归因到本会话的改动上）

- 用户运行的是 `/Applications/SpeakOut.app`，**v1.10.0 build 241**，
  其 `libnative_input.dylib` 时间戳 **8/14 16:26**。
- `strings` 查该 dylib：`Clipboard tx` 匹配数 **0** —— 本会话（8/16）对剪贴板
  事务协调器的全部改动**都不在这个二进制里**。
- 结论：**这是线上现存缺陷的一次真实复现，不是本会话改出来的。**

### 日志能证明什么

日志目录取自 plist（`flutter.log_directory = ~/Apps/speakout/log`），verbose 已开。

事故时间窗三次连续 PTT（均为 toggle 模式，模式 ptt，云端 Volcengine ASR）：

| 结束时刻 | ASR 结果 | inject/save done |
|---|---|---|
| 19:31:00.97 | 106 字 `#9d2ced` | 19:31:02.11 |
| 19:31:53.56 | 39 字 `#be820b` | 19:31:53.90 |
| 19:32:13.51 | 40 字 `#2df7c4` | 19:32:14.84 |

由此**可以排除**两条：

1. **「`CLIPBOARD_RESTORE_DELAY_MS`(800ms) 内连注两次」不成立。**
   相邻两次注入间隔 51.8s 和 20.9s，差了一到两个数量级。
2. **AI 润色 / 打字机流式路径没有参与。** `inject/save done` 距 ASR 返回只有
   ~40ms，中间没有 LLM 调用；走的是一次性 `inject_via_clipboard`，
   不是 `inject_clipboard_begin/chunk/end`。

三次 ASR 结果内容哈希互不相同，说明**识别本身没错**，错在识别之后。

### 日志不能证明什么 —— 这本身是最该修的一条

`native_input.m` 里 **`inject_via_clipboard` 全函数零日志**。
出货 dylib 里 clipboard/inject 相关字面量只有 3 条，全属于流式路径。

于是这次事故在原生日志里**一行痕迹都没有**：
不知道快照拍到了什么、`clearContents` 返回的 changeCount 是多少、
Cmd+V 发出前剪贴板里到底是不是我们刚写的文字、800ms 后的还原走没走。

**文本注入是这个产品最核心的一步，而它在日志里完全不可见。**
排查只能靠推理，这是这轮最该先补的窟窿。

### 假设 · 判断原因（未验证，按可能性排序）

**A. 还原被跳过，上一次的注入文字滞留在剪贴板。**
出货代码的还原判据是：

```objc
dispatch_after(800ms, ...) {
  if (pasteboard.changeCount != ourChangeCount) return; // 跳过还原
  ...
}
```

只要这 800ms 内有任何人动过剪贴板，还原就被跳过，**我们注入的文字永久留在剪贴板**。
本机没有第三方剪贴板管理器，但系统的 `SSPasteboardHelper`（屏幕共享剪贴板同步代理）
在跑，它会观察并可能触碰剪贴板。

**B. Cmd+V 早于新内容生效，贴出了剪贴板里的旧内容。**

```objc
[pasteboard setString:newText forType:NSPasteboardTypeString];
usleep(10000);            // 10ms —— 纯猜的等待，没有任何校验
post_command_key(9, kCGHIDEventTap);   // Cmd+V
```

写完剪贴板只睡 10ms 就发 Cmd+V，**没有任何一步确认目标进程看到的已经是新内容**。
跨进程 pasteboard 可见性没有时限保证，机器忙的时候这 10ms 完全可能不够。

**A + B 叠加正好解释现象**：A 让上一次的注入文字留在剪贴板，
B 让这一次的 Cmd+V 贴出的仍是那份旧内容 —— 用户看到的就是「上一次识别的文字」。

需要强调：**A、B 都是推理，日志给不出证据**（因为根本没日志）。
在补上日志、拿到一次带证据的复现之前，不把任何一条当成定论。

### 措施

1. **给一次性注入路径补齐日志**（本轮必做）：快照条数、`clearContents` 返回值、
   发 Cmd+V 前剪贴板里实际内容的指纹、还原走没走 / 为什么没走。
   没有这些，下次复现照样只能猜。
2. **把「睡 10ms」换成「校验通过才发 Cmd+V」**：写完之后轮询确认
   `stringForType:` 读回来的就是我们写的那份，确认不到就放弃这次注入
   （宁可不注入，也不要把上一次的文字贴进用户的文档）。
3. 还原被跳过时**记明原因**（changeCount 对不上 / 快照不可信），
   把「静默跳过」变成「日志里查得到」。

本会话正在重写的事务协调器**并没有修掉这两条** —— `tx_paste_locked` 里同样是
`usleep(10000)` 之后直接发 Cmd+V。所以这不是「已经修好了、只是没发版」，
而是一条独立的、仍然存在于最新代码里的缺陷。

## 第二轮：把「猜」变成「查得到 + 拦得住」

### 措施（已实施）

1. **发 Cmd+V 之前校验剪贴板确实生效。**
   `tx_paste_locked` 写完之后轮询 `stringForType:`，读回来与写进去的一致才发键，
   最多等 200ms（40 × 5ms）；超过 5 次轮询才拿到会记一行「花了多少 ms」。
   **校验不过就不发 Cmd+V** —— 宁可这次注入失败，也绝不把上一次的识别结果
   贴进用户文档。这是取代原来那句 `usleep(10000)` 的关键改动：
   把「等 10ms 应该够了吧」换成「确认到了才动手」。

2. **注入失败不再静默。** `inject_text` 从 `void` 改成返回 `int`
   （Linux/Windows 两个实现同步改签名 —— Dart 侧按 `Int32` 绑定，
   那边若还是 `void`，读到的返回值是垃圾）。
   `CoreEngine` 收到 false 时发 `EngineStatus.error("注入失败，文字已存到聊天记录")`，
   并且**照常把文字写进聊天记录**——那是用户唯一能找回这段话的地方。

3. **一次性注入路径补日志**：长度、代次、是否失败、剪贴板迟到多久、
   还原走没走 / 为什么没走（changeCount 对不上 vs 快照不可信）。
   下次再复现，日志里查得到，不用再靠推理。

### 仍未解决 / 需要真机验证

- **候选 A（还原被跳过导致上一次的文字滞留剪贴板）没有被这轮改动消除。**
  本会话的事务协调器让「800ms 内连注两次」不再丢原内容，但「800ms 内**别人**
  动了剪贴板 → 跳过还原 → 我们的文字留在剪贴板」这条依然成立。
  这是有意的：那种情况下用户手里是他自己刚复制的东西，硬还原会盖掉它。
  代价是我们的注入文字可能留在剪贴板里。**这是取舍，现在至少日志里看得见。**
- 本轮改动**尚未在真机验证**。需要装上新版后复现一次，确认：
  (a) 正常注入时日志有 `Clipboard tx: inject ...` 行；
  (b) 制造慢速场景时能看到「pasteboard took Nms」或「never reflected」；
  (c) 注入失败时 UI 真的弹出提示。

## 第三轮：拿到决定性证据，机制定名

### 现象（补充）

用户提出假设：**云端模式下从送音频到拿回文字这段太长，剪贴板还没开始动。**

### 判断原因

这个假设可以直接用日志证伪 —— **我们自己合成的 Cmd+V 带 `SPEAKOUT_SYNTHETIC_MARK`，
在 tap 回调开头就被滤掉，不会进日志**。所以日志里出现的 `code=9` 一定是真人按的。
左 Command 的设备位是 `0x8`，基线是 `0x100`，因此真实 Cmd+V 就是 `mods=0x108`。

| 时刻 | 事件 |
|---|---|
| 19:32:13.51 | 最后一次录音结束 |
| 19:32:14.85 | 注入完成（40 字 `#2df7c4`），**此后再无任何录音** |
| 19:37:09.97 / :11.85 / :23.05 | `code=9 mods=0x108` —— 真实 Cmd+V ×3 |

**粘贴发生在注入之后 4 分 55 秒。** 由此：

- **用户的假设不成立**：粘贴根本不在任何 ASR 等待窗口里，差了 5 分钟。
- **第一轮的候选 B（10ms 传播竞态）也不是本次原因**：那影响的是注入当下，
  管不到 5 分钟后的一次手动粘贴。
- **只剩候选 A，并且被坐实**：那次注入的文字一直留在剪贴板里没被还原，
  用户 5 分钟后 Cmd+V 贴出来的自然就是它。

顺带量了云端 ASR 耗时（29 个样本）：**最小 300ms / 中位 379ms / 最大 5221ms**。
中位数可以接受，**最大 5.2 秒是真问题**，但与本次故障无关，另记。

### 根因

还原判据错了。出货代码（以及本会话此前的全部改动）都在比 `changeCount`：

```objc
if (pasteboard.changeCount != ourChangeCount) return; // 跳过还原
```

**`changeCount` 会被任何「重新声明 pasteboard」的旁观者推高，不只是用户复制。**
这台机器上正跑着 `SSPasteboardHelper`（屏幕共享的剪贴板同步代理），
它一动，我们就永远判定「用户易主」而跳过还原 —— 注入的文字于是永久滞留。

真正要区分的是**内容**：剪贴板里现在还是不是我们放进去的那份？
是 → 没人真正接管过，还原天经地义；不是 → 用户确实换了，别去盖他的。

### 措施

`tx_finish_locked` 的判据从「`changeCount` 没变」改成
「`stringForType:` 读回来的内容 == 我们最后写进去的 `_txLastInjected`」。
本事务一次都没写过剪贴板时（比如 begin/end 之间 LLM 就失败了）退回比 `changeCount`。

### 验证结果

- 新增 3 条断言（还原判据比内容 / 发键前校验 / 注入失败可上报），
  2 个变异探针确认能抓到（退回只比 changeCount、退回固定 10ms 等待）。
- clang 零警告，全量测试通过。
- **真机验证仍未做** —— 需要装机后复现「注入 → 隔几分钟 Cmd+V」，
  确认贴出来的是用户自己的剪贴板内容而不是识别结果。

### 复盘

- **我把这条判成了「有意的保守行为」，判错了。** 第二轮我还写下
  「那种情况下用户手里是他自己刚复制的东西，硬还原会盖掉它 —— 这是取舍」。
  错在我默认了「changeCount 变了 == 用户换了内容」，而实际上**任何旁观者
  都能推高 changeCount**。用错误的判据去论证一个取舍，取舍本身就是假的。
- 这正是本会话反复出现的同一个毛病：**给自己没修的东西写辩护性注释**。
  上一次的教训是「要么修、要么写未修」，这次更进一步：
  **写「这是取舍」之前，先确认判据本身是对的。**
- 用户的假设虽然不成立，但**方向性提示有价值** —— 它逼我去查真实按键时间戳，
  而那正是把候选 A 从「推理」变成「证据」的那一步。
  没有那个追问，我会停在「A 和 B 都有可能」。
